# Build Talon in Swift, shim the C

**Build all of Talon in Swift 6.4, with one small C/Objective-C shim target for private headers and the NVMe SMART CFPlugIn vtable.** Use SwiftUI for the app and widget, with an AppKit spine for the menu bar panel and the process table. Use Swift Charts over pre-downsampled data, SQLite through GRDB 7.12 for tiered history, and the Swift XPC API over a launchd Mach service to reach a root LaunchDaemon installed by `sudo make install`. The deciding factor is sharing, not raw speed. Talon has four consumers (daemon, CLI, app, widget) that must agree on one model and one IPC schema, and only an all-Swift build gives one source of truth without code generation. WidgetKit is SwiftUI-only, so every alternative still includes Swift and adds a second stack on top. The phase-0 spikes already cleared the risks that might have argued for another language: Swift and C reached every needed API, a 1 Hz sweep of ~700 processes cost **0.35% CPU**, and an ad-hoc-signed Swift daemon worked end to end over NSXPCConnection. Rust is the only credible rival. It is a good sampler language, but for one developer it brings a second toolchain, an FFI layer whose Swift 6 async support is still "partial", and no native NSXPCConnection. The real risks now are signing (widgets, App Groups and XPC peer requirements under ad-hoc or free Personal Team signing), private-API drift (the IOReport CPU energy counters already read zero on macOS 27), and a few SwiftUI performance limits. A handful of short hands-on spikes on the M5 settles each of them.

## Swift plus a thin C shim wins on every axis that matters for one developer

The comparison comes down to four questions. Can the language reach the private APIs? Can it speak XPC natively? Can it share types with SwiftUI and WidgetKit? How many toolchains does it add? Swift with a C target is the only candidate that answers all four well. Swift 6.3 added `@c` and `@implementation`, which let Swift implement functions declared in a C header with checked signatures. That makes CF and IOKit notification callbacks straightforward. 6.3 also added module selectors (`ModuleA::name`) for the name clashes private headers tend to cause ([Swift 6.3 Released](https://swift.org/blog/swift-6.3-released/)). Swift 6.2 added `InlineArray` and `Span`, so the per-tick pid and `rusage_info_v6` buffers can stay allocation-free ([Swift 6.2 Released](https://www.swift.org/blog/swift-6.2-released/)). Phase 0 already showed the sweep costs 0.35% CPU, so runtime overhead is settled. No published Swift-vs-Rust daemon footprint comparison exists, and the difference is at most a few MB of RSS on a 16 GB machine.

| Criterion | Swift 6.4 + C shim | Rust core + SwiftUI | Go | Zig/C | Web/Flutter shell |
|---|---|---|---|---|---|
| Private C, CF, IOKit, IOReport | Excellent via C target | Good (`objc2-*`, macmon ships it) | cgo for everything | Good for C, no ObjC | Needs a native core anyway |
| NSXPCConnection / Swift XPC | Native | Awkward; socket or C XPC instead | No; Unix socket | No; socket or C XPC | No |
| Signals, `posix_spawn`, jetsam attrs | Direct syscalls, DispatchSource | Direct via libc | Runtime owns signals; cgo for jetsam | Direct | N/A |
| Share models with SwiftUI and widget | One module, no codegen | UniFFI codegen plus wrapper classes | None | None | None; widget still Swift |
| Toolchains | 1 | 2 | 2 | 2 | 2–3 |

Rust deserves the strongest case against Swift, and it has a real one. **macmon, a Rust tool, reads IOReport and AppleCLPC energy data in production** and was quick to track Apple's private-API changes ([vladkens/macmon](https://github.com/vladkens/macmon)). Rust's borrow checker also beats Swift 6's `Sendable` model for concurrency safety. What undoes it is the boundary. UniFFI's own docs still call Swift 6 support **"partial"**: async code is not `Sendable`, and a Rust panic in a non-throwing Swift function becomes an uncatchable fatal error ([UniFFI Swift overview](https://mozilla.github.io/uniffi-rs/latest/swift/overview.html)). UniFFI objects also cannot drive SwiftUI updates without hand-written wrapper classes ([uniffi-rs#2145](https://github.com/mozilla/uniffi-rs/issues/2145)), and a 2025 integration write-up reads mostly as a troubleshooting guide for Xcode 26 linking problems ([Integrating Rust with SwiftUI using UniFFI](https://artmis-blog.netlify.app/posts/integrating-rust-with-swiftui)). Because Talon already splits daemon from app at a process boundary, a Rust `talond` would not even need UniFFI for the app. It would need a Unix socket and a serialization schema defined twice, once in Rust and once in Swift. If learning Rust is itself a goal, the clean experiment is a standalone Rust CLI sampler alongside Talon, not a split core.

Go and Zig fall out quickly. Go's macOS SMC libraries are cgo over IOKit ([gosmc](https://github.com/charlie0129/gosmc)). batt, the closest open-source analogue to Talon (root daemon, CLI and menu bar GUI), ended up on a **Unix domain socket rather than XPC** ([charlie0129/batt](https://github.com/charlie0129/batt)). Go's runtime also owns signal handling and does not expose `posix_spawnattr_setjetsam_ext`, both central to Talon's enforcement. Zig's `@cImport` handles libproc and IOKit headers well, but has no Objective-C or blocks story, so XPC and IOKit notification blocks would need C shims anyway.

Swift 6 strict concurrency does add friction in this kind of code, though it is manageable. The pattern is to keep pointer-heavy and signal-heavy code synchronous inside one owner and let only `Sendable` value snapshots escape. Concretely, run the SIGSTOP/SIGCONT duty cycler on a dedicated serial `DispatchQueue` with a `DispatchSourceTimer` rather than cooperative-pool `Task.sleep`, and guard its state with the Synchronization module's `Mutex`, which wraps `os_unfair_lock` ([SE-0433](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0433-mutex.md)). Handle the daemon's own SIGTERM through `DispatchSource.makeSignalSource`, and run a SIGCONT-all sweep at startup and on termination so a crash never leaves a process frozen. Swift 6.4 adds `~Sendable` for explicitly non-Sendable wrappers around IOReport subscriptions and HID clients, plus `@diagnose` for auditing unsafe regions ([Michael Tsai, Swift 6.4](https://mjtsai.com/blog/2026/06/24/swift-6-4/)). Turn on default MainActor isolation in the app target only. `talond` and the core library stay nonisolated, with explicit actors.

The phase-0 finding that **IOReport CPU energy counters read zero on macOS 27** has nothing to do with language. macmon documents the same break: the Energy Model channels now require a private entitlement only Apple-signed `powermetrics` holds, and macmon moved to hidden AppleCLPC reports with opaque, per-chip mappings ([vladkens/macmon](https://github.com/vladkens/macmon)). Every language would hit the same wall. The design consequence is to put each private API behind its own small shim with an "unavailable" state. Treat per-cluster CPU power as optional, and derive system power from the battery and adapter sensors, which phase 0 confirmed work.

## A SwiftUI app on an AppKit spine is the only route to Apple-premium

The premium-UI requirement settles the shell question even more clearly than the core requirements settle the language. On a SwiftUI/AppKit stack, Liquid Glass, MenuBarExtra, WidgetKit, trackpad haptics, SF Symbols and spring animations are all first-class. Every other shell has to reach them through bridges. Tauri gets Liquid Glass through `window-vibrancy`, which needs `macOSPrivateApi: true` and a transparent window ([window-vibrancy](https://docs.rs/crate/window-vibrancy/latest/source/src/macos/mod.rs)). It also has to build its widget as a separate Xcode project, then copy and re-sign the `.appex` ([tauri-plugin-widgets macOS setup](https://docs.rs/crate/tauri-plugin-widgets/0.4.3/source/docs/guide/setup/macos.md)). Electron needed a fix for a macOS 26 WindowServer GPU-load spike caused by overriding a private `cornerMask` API ([Electron commit](https://ayakael.net/mirrors/electron/commit/c15d8a4a37310636dfbbbeb83118bc6e00b81e7a)). The most visible 2026 move to web UI, Raycast 2, was made for Windows support and hiring, and **memory rose from about 200–300 MB to about 350–450 MB** ([Raycast blog, May 2026](https://www.raycast.com/blog/a-technical-deep-dive-into-the-new-raycast)). A resource-ceiling app that itself uses 400 MB would undercut its own purpose.

Within the Swift stack, the evidence points to SwiftUI for most views, with AppKit in two specific places. The first is the Processes table: about 700 rows, grouped by app, sortable, refreshing at 1 Hz. WWDC25 claimed 6x faster loading and 16x faster updating for SwiftUI List and Table on macOS 26. Michael Tsai doubts this reaches NSTableView parity, because the gains came from scheduling and lazy loading rather than architecture ([mjtsai, June 2025](https://mjtsai.com/blog/2025/06/18/swiftui-at-wwdc-2025/)). Into the macOS 27 cycle, developers still report SwiftUI collections as "unusably slow" for some rebuilds, and that **UIKit "still remains streets ahead"** for large collections ([mjtsai, SwiftUI in appleOS 27](https://mjtsai.com/blog/2026/06/19/swiftui-in-appleos-27/)). So start the Processes view as an NSOutlineView wrapped in NSViewRepresentable. Give it fixed row heights, identity keyed on PID plus start time, and targeted `reloadData(forRowIndexes:columnIndexes:)` calls. Cells can re-render from `@Observable` row models through the `NSObservationTrackingEnabled` key, available since macOS 15 ([steipete.me](https://steipete.me/posts/2025/automatic-observation-tracking-uikit-appkit)).

The second is the menu bar. MenuBarExtra is fine for a prototype, but `SettingsLink` and `openSettings` do not work reliably from it on macOS 26 ([steipete.me](https://steipete.me/posts/2025/showing-settings-from-macos-menu-bar-items)), wrapped AppKit views reportedly do not display inside it ([zenn.dev/kyome](https://zenn.dev/kyome/articles/9f0f1969b5553c)), and its pop-up does not animate ([FluidMenuBarExtra](https://swiftpackageregistry.com/wadetregaskis/FluidMenuBarExtra)). Plan from day one to move to an NSStatusItem with a borderless, non-activating NSPanel hosting SwiftUI. Manage it through an `NSApplicationDelegateAdaptor` alongside the SwiftUI App lifecycle.

Swift Charts can deliver the chart quality Talon wants, as long as it never receives raw data. Apple forum reports show chart setup slowing from **about 20k points**, with windows that "barely resize" at 100k. The poster fixed it with off-main-thread LTTB downsampling ([Apple Dev Forums 740314](https://developer.apple.com/forums/thread/740314)). Use the vectorized `LinePlot` and `AreaPlot` APIs for the dense series ([WWDC24 10155 notes](https://wwdcnotes.com/documentation/wwdc24-10155-swift-charts-vectorized-and-function-plots/)), and Mark APIs for the ceiling `RuleMark` and event annotations. The draggable ceiling is a `chartOverlay` plus a `ChartProxy` mapping from pointer y to a value ([Apple ChartProxy docs](https://developer.apple.com/documentation/charts/chartproxy)), firing `NSHapticFeedbackManager.defaultPerformer.perform(.alignment, ...)` only when the snapped value changes. Apple restricts haptics to user-initiated actions, and the system suppresses them when no finger is on the Force Touch trackpad ([Apple: NSHapticFeedbackManager](https://developer.apple.com/documentation/appkit/nshapticfeedbackmanager)). The storage tiers described below cap every view at roughly 2k points, which leaves Swift Charts well inside its comfort zone. Use Canvas only if a dense grid of per-process sparklines is wanted. Metal is not justified for this workload.

Liquid Glass needs little custom work. Standard NavigationSplitView sidebars, toolbars and sheets adopt it automatically on the macOS 26/27 SDK. Use `glassEffect` and `GlassEffectContainer` only for floating chrome, such as the range picker, the "Set ceiling" pill and button clusters in the menu bar panel ([Apple: Applying Liquid Glass to custom views](https://developer.apple.com/documentation/SwiftUI/Applying-Liquid-Glass-to-custom-views)). Keep chart and table surfaces opaque for legibility, and test under Reduce Transparency and the opaque menu bar setting, since the transparent Tahoe menu bar draws legibility complaints ([MacMost](https://macmost.com/how-to-tame-liquid-glass-on-your-mac.html)). Widgets are a summary surface, not a live one. macOS throttles timeline refreshes ([tauri-plugin-widgets transport.rs](https://docs.rs/crate/tauri-plugin-widgets/latest/source/src/transport.rs)), so the menu bar panel at 1 Hz is the live view, and widgets show minute-level summaries plus AppIntent buttons for "Care" actions.

## Tiered SQLite through GRDB keeps a year of history under 350 MB

Storage choices hinge on schema design more than on the database. Writing every PID every second into any row store costs gigabytes per day. The research notes estimate that the naive design, 60.5 M rows/day committed each second, would write roughly **4–6 GB/day, or about 1.5–2 TB/year**, to a 512 GB SSD. By the same arithmetic, a tiered per-app design with batched commits writes about **30–100 MB/day**, and its steady-state database settles near **0.2–0.35 GB**. These figures are unmeasured estimates, but the mechanism behind them is documented. In WAL mode every changed page is written at least twice, once to the WAL and again at checkpoint, and with `synchronous=NORMAL` only checkpoints issue a sync ([SQLite WAL](https://www.sqlite.org/wal.html)). Each tiny one-second commit therefore pays full-page overhead, while batching amortizes it.

| Tier | Where | Resolution | Content | Retention |
|---|---|---|---|---|
| T0 | Daemon RAM ring buffer | 1 s | ~60 system series; per-app totals; per-PID current snapshot plus ~5 min ring | 1 h, never persisted |
| T1 | `sys_10s` | 10 s | System series, one wide row | 48 h–7 d |
| T2 | `sys_1m`, `app_1m` | 1 min | min/avg/max per series; per-app (top-N plus "other") | 90 d / 30 d |
| T3 | `sys_1h`, `app_1h` | 1 h | min/avg/max/sum | Forever |
| Events | `event` | Irregular | Ceiling breaches, freezes, kills, panics, top-N snapshot | Forever, committed immediately |

Downsample in daemon memory using running accumulators, not with SQL `INSERT … SELECT`. Commit tiers every 60 s or more. Use WAL with `synchronous=NORMAL`, which SQLite calls "the best balance between performance and safety for most applications running in WAL mode" ([SQLite PRAGMA](https://www.sqlite.org/pragma.html)), plus `journal_size_limit` around 8 MB, `temp_store=MEMORY`, `WITHOUT ROWID` tables keyed on `(ts, app_id)`, no secondary indexes, and integer-scaled values (centi-degrees, milliwatts, KiB). Store min, max and avg per bucket so coarse tiers still show thermal and memory spikes, as Netdata's 1 s / 1 min / 1 h tiers do ([Netdata disk & retention](https://learn.netdata.cloud/docs/netdata-agent/resource-utilization/disk-&-retention)) and as Stats' one-minute buckets with a 60 s flush do ([exelban/stats DB.swift](https://raw.githubusercontent.com/exelban/stats/master/Kit/plugins/DB.swift)). Apple's own always-on power logging uses SQLite with per-app aggregate tables ([Plaso powerlog parser](https://plaso.readthedocs.io/en/latest/_modules/plaso/parsers/sqlite_plugins/ios_powerlog.html)), a strong precedent for this exact role.

GRDB is the clear library choice. GRDB 7 adopted the Swift 6 language mode ([Swift Forums: GRDB 7 is out](https://forums.swift.org/t/grdb-7-is-out/77465)), and **7.12.0 shipped on 1 November 2026** with a fix for an SQLite WAL snapshot bug ([GRDB releases](https://github.com/groue/GRDB.swift/releases)). The rejected options each fail for a specific reason. SwiftData and Core Data are object graphs with documented bulk-insert slowness ([Hacking with Swift](https://www.hackingwithswift.com/quick-start/swiftdata/how-to-batch-insert-large-amounts-of-data-efficiently)). Realm's SDK reached end-of-life in September 2025 ([MongoDB deprecation](https://www.mongodb.com/docs/atlas/device-sdks/deprecation.md)). DuckDB allows only one read-write process on a native file ([DuckDB concurrency](https://duckdb.org/docs/2.0/connect/concurrency.html)), its Swift API is "subject to change between minor version updates" ([duckdb-swift](https://github.com/duckdb/duckdb-swift)), and its analytics advantage means nothing at a few hundred MB.

Only the daemon should open the database. GRDB's sharing guide warns that observation "features are not able to detect database changes performed by other processes", that read-only connections need persistent `-wal` and `-shm` files, and that you should "always consider sharing plain files" first ([GRDB DatabaseSharing](https://raw.githubusercontent.com/groue/GRDB.swift/master/GRDB/Documentation.docc/DatabaseSharing.md)). A long-lived reader can also stop checkpoints and let the WAL "grow without bound" ([SQLite WAL](https://www.sqlite.org/wal.html)). So the daemon owns `/Library/Application Support/Talon/talon.sqlite` through a `DatabasePool` and serves typed range queries over XPC as compact `[Int64]`/`[Float]` arrays. The app merges those results with T0 live data, and the widget reads a few-KB JSON snapshot from its container.

## The root helper is the security boundary, so validate peers before anything else

IPC should be XPC over a launchd `MachServices` name, and the Swift XPC API is the right long-term surface. `XPCSession(machService:)` has existed since macOS 14 and exchanges `Codable` values directly ([Apple: XPCSession](https://developer.apple.com/documentation/xpc/xpcsession/init(machservice:targetqueue:options:cancellationhandler:).md)). On macOS 26+, `XPCListener(service:requirement:)` drops peers that fail an `XPCPeerRequirement` before any handler runs ([Apple: XPCListener](https://developer.apple.com/documentation/xpc/xpclistener/init(service:targetqueue:options:requirement:incomingsessionhandler:).md)). Define one `Codable` `TalonRequest` enum and one `TalonReply` enum. A single enum also avoids a known Codable-send failure ([Apple Forums 798938](https://developer.apple.com/forums/thread/798938)). That removes NSXPCConnection's `@objc` protocols and NSSecureCoding and fits Swift 6's `@Sendable` handlers. NSXPCConnection with `.privileged` is what phase 0 proved, and Apple DTS's own working sample still uses it ([Apple Forums 799910](https://developer.apple.com/forums/thread/799910)). Keep it as the known-good fallback, port the message schema first, and swap the transport only once the Swift API passes the spike below. Stream metrics to the menu bar by polling at 1 Hz, which is cheap for local XPC, wrapped in an `AsyncStream`. gRPC and localhost HTTP add auth work and lose launchd on-demand launch. A root-owned Unix socket, batt's model, stays plan B if signing requirements become unworkable.

Install the helper the way phase 0 did it. `sudo make install` runs `launchctl bootout`, installs the binary `root:wheel 755` into `/Library/PrivilegedHelperTools` and the plist `644` into `/Library/LaunchDaemons`, then runs `launchctl bootstrap system` and `kickstart -k`. SMAppService.daemon is Apple's supported path, but with free-profile signing it fails with "Operation not permitted" and then works "after changing literally nothing", and Apple DTS says it does not know of an Apple daemon that uses it ([Apple Forums 799910](https://developer.apple.com/forums/thread/799910)). It also keeps sticky approval state that needs `sfltool resetbtm` to clear ([Apple Forums 802443](https://developer.apple.com/forums/thread/802443)). Treat it as optional polish. Never use SMJobBless, which is deprecated and built around Developer ID requirements.

The threat model is concrete, because recent CVEs come from helpers with exactly this shape. **Stats' SMC helper accepted any XPC client (CVE-2025-21606)** ([cvefeed](https://cvefeed.io/vuln/detail/CVE-2025-21606)). **Pearcleaner's helper accepted unauthenticated clients and ran caller-supplied shell commands, a local root escalation (CVE-2025-54595, CVSS 7.3)** ([CIRCL](https://cve.circl.lu/vuln/cve-2025-54595)). Several 2026 audio-vendor helpers validated a PID's signature and were exploited through PID reuse ([NVD CVE-2026-24071](https://nvd.nist.gov/vuln/detail/CVE-2026-24071)). Signing complicates the defence. Ad-hoc signatures carry no Team ID, so `isFromSameTeam` and `TeamIdentifier` requirements cannot match. A signing-identifier-only requirement is spoofable, because anyone can ad-hoc sign with any identifier. A free Personal Team "Apple Development" certificate does carry a Team ID ([Apple Forums 799910](https://developer.apple.com/forums/thread/799910)). That would enable a Lightweight Code Requirement of `TeamIdentifier` plus `SigningIdentifier.in(...)` ([Apple Forums 815147](https://developer.apple.com/forums/thread/815147)), but nobody has confirmed it works.

The hardening therefore has to hold even under pure ad-hoc signing. Identify each caller by audit token, never PID, and require its euid to equal the console user's uid or 0. Resolve every target with `proc_pidinfo`, require it to share the caller's uid, and re-check right before acting. Refuse PID ≤ 1, WindowServer, root-owned processes and talond itself. Expose only typed verbs such as `setMemoryCap(pid:bytes:)` and `freeze(pid:)`, never exec passthrough. Have `talon run` spawn the child in the CLI as the user and register its PID with talond, rather than letting root spawn anything. Log every privileged action through `os.Logger`. What remains is a same-uid attacker freezing that user's own processes, which `kill` already allows, so the helper adds no privilege escalation.

## One SwiftPM package, one XcodeGen project, one Makefile

SwiftPM cleanly builds the daemon, the CLI and all shared libraries. It cannot produce app extensions, so the app and widget need an Xcode project. XcodeGen generates that project from YAML in under a second and can be dropped by committing the output, while Tuist is heavier ([Medium: Tuist and XcodeGen](https://medium.com/@mobile_44538/tuist-and-xcodegen-7a35e02c278a)). Keep the daemon and CLI out of Xcode and build them with `swift build -c release`. Embed an Info.plist through `-sectcreate __TEXT __info_plist` where a bundle identifier is needed for signing. One Xcode 27 trap applies: the dependency scanner **requires every reachable Clang module to have a unique name** ([Michael Tsai, Swift 6.4](https://mjtsai.com/blog/2026/06/24/swift-6-4/)), so the private-header module map must not reuse a name like `IOReport` that an SDK module might claim. Prefix it, for example `TalonPrivate`.

```
talon/
  Package.swift                 # TalonKit: libraries + talond + talon
  Sources/
    TalonPrivate/               # C/ObjC target: private decls (IOReport, IOHIDEventSystem,
                                #   memorystatus_control, posix_spawnattr_setjetsam_ext,
                                #   responsibility_get_pid_responsible_for_pid) + NVMe SMART shim
    TalonModel/                 # Sendable/Codable value types: samples, policies, limits
    TalonIPC/                   # TalonRequest/TalonReply enums, Mach service name, protocol version
    TalonSensors/               # one file per private API, each with an "unavailable" state
    TalonCore/                  # sampler, aggregator, policy engine, enforcer (pure, injectable)
    TalonStore/                 # GRDB schema, tiers, retention (daemon-only)
    talond/                     # XPCListener, peer validation, launchd lifecycle, signal sources
    talon/                      # swift-argument-parser CLI: status, run, cap, freeze, history
  Tests/                        # Swift Testing: policy tables, Codable round-trips, exit tests
  App/
    project.yml                 # XcodeGen: TalonApp (SwiftUI + AppKit spine) + TalonWidget
    TalonApp/                   # depends on TalonModel + TalonIPC only
    TalonWidget/                # reads JSON snapshot; AppIntents for Care actions
  launchd/dev.kanishk.talond.plist
  Makefile                      # build, test, sign, verify-req, install, uninstall, logs
```

The app and widget link only `TalonModel` and `TalonIPC`. They never link the sensor or store code. Swift Testing is mature enough to be the only test framework ([Swift 6.2 Released](https://www.swift.org/blog/swift-6.2-released/)). Its exit tests cover "a frozen child is resumed when the daemon dies" without crashing the runner, and parameterized tests cover limit parsing and the "may this caller touch this PID?" policy table, which runs as pure functions over an injected process table, so tests never need root. The Makefile signs with `codesign -s - --options runtime -i dev.kanishk.talond` (or a Personal Team identity), runs a `verify-req` target that checks the listener's requirement string against the built binaries with `codesign -R`, and offers `make logs` as a `log stream` filtered to the `dev.kanishk.talon` subsystem.

| Avoid | Why |
|---|---|
| Rust, Go or Zig for the core | Second toolchain, no native XPC, duplicated model types; Go's runtime owns signals |
| Tauri, Electron, Flutter, Compose shells | Private-API glass hacks, separate widget project, Raycast-scale memory |
| SwiftUI `Table` for the 700-row live list | Reported hangs and lag at large live row counts; NSOutlineView is proven |
| MenuBarExtra as the final panel | Settings, animation and AppKit-hosting bugs on macOS 26 |
| Raw 24 h+ series fed to Swift Charts | Degrades from ~20k points; downsample to ≤2k |
| Per-PID per-second rows on disk, or 1 s commits | Estimated TB/year of writes |
| SwiftData, Core Data, Realm, DuckDB for history | Slow bulk inserts, deprecation, single-writer lock, unstable API |
| App or widget opening the root-owned SQLite file | WAL permission issues, blind observation, checkpoint starvation |
| SMJobBless; loading the daemon from DerivedData | Deprecated; a user-writable root binary is an escalation path |
| PID-based peer checks, generic exec verbs, identifier-only requirements | The exact bugs behind 2025–2026 helper CVEs |
| Hard dependency on IOReport CPU/ANE energy | Reads zero on macOS 27; entitlement-gated |

## Eight short spikes settle what the research could not

The architecture is decided. The open questions are all signing or performance facts that only the actual Mac can answer, and each takes minutes to an hour.

| # | Question | Test on the M5 | If it fails |
|---|---|---|---|
| 1 | Does a free Personal Team identity satisfy an `XPCPeerRequirement` (Team ID plus signing IDs) on macOS 27? | Sign app, CLI and daemon with the Personal Team; validate with `codesign -R`; connect | Ad-hoc plus audit-token/uid checks, optional cdhash pin |
| 2 | Does the widget register and read a `<TeamID>.`-prefixed App Group under Personal Team signing, installed in /Applications? | Minimal widget reading a snapshot | Write into the widget's own container (dev workaround), drop the widget, or pay $99 for ADP |
| 3 | Does the Swift XPC API match phase-0 NSXPCConnection with `.privileged`, and does it expose the peer audit token? | Port `status()` to `XPCListener`/`XPCSession` | Stay on NSXPCConnection |
| 4 | Is SwiftUI `Table` acceptable at ~700 grouped rows refreshing at 1 Hz on macOS 27.2? | Side-by-side against NSOutlineView; measure scroll, selection, CPU | NSOutlineView (default plan) |
| 5 | Where does vectorized `LinePlot` stop feeling smooth? | Sweep 2k, 20k, 100k points; resize and 1 Hz append | Tighten the downsampling budget |
| 6 | What are real write volume, distinct-app count and daemon RSS? | 24 h soak: `ri_diskio_byteswritten` on talond, `footprint -p`, count responsible apps | Lengthen commit interval to 300 s; shrink top-N |
| 7 | Can a root daemon write the widget snapshot into the user's container without TCC or ownership trouble? | Daemon writes JSON into the user's container | App writes the snapshot instead |
| 8 | Is there a usable CPU power source now that IOReport energy reads zero? | Probe AppleCLPC reports as macmon does; compare with battery/adapter system power | Show system power only; label per-cluster power unavailable |

Two smaller checks belong in the same session. Confirm whether the reported macOS 27 repeated-popover crash ([mjtsai, SwiftUI in appleOS 27](https://mjtsai.com/blog/2026/06/19/swiftui-in-appleos-27/)) is fixed in 27.2. Confirm whether SwiftUI's `.sensoryFeedback` reaches the trackpad as reliably as calling NSHapticFeedbackManager directly; until then, call AppKit.

## Conclusion

On a single-developer, single-Mac project, the language debate is really about where the seams fall. Talon already has one unavoidable seam, the root/user process boundary, and an all-Swift build makes that the only one, with one schema crossing it. Every alternative adds a second seam (FFI, a socket protocol or a second UI stack) without removing any Swift, because WidgetKit and Liquid Glass require it anyway. The spikes have already shown that performance gives no reason to pay that cost.

The risk has moved from engineering to platform policy. Talon's fragile points are Apple's decisions: which counters need entitlements, what ad-hoc signing may do, and how widgets and App Groups are provisioned. The architecture should treat those as variables. That means a sensor layer where any reading can be "unavailable", security that holds under the weakest signing tier, and a menu bar panel that works even if the widget never ships. The $99 developer membership becomes a realistic upgrade if spikes 1 and 2 fail.
